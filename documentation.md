# g9-Battle-Scene — manifest description

This file records the full `description` for the **g9-Battle-Scene** mod
(`manifest.json`). The manifest's own `description` field is capped at
**80 characters** (a studio rule, so the Mod Manager row and the generator
listing stay readable), so the complete text lives here and the manifest
carries only a short summary.

## Current description (full)

PATCH 4.0.2: a non-nicknamed Pokemon is named by its SPECIES in every battle announcement and HUD label, not by its id. `battle_screen.lua`'s `displayName` now resolves a battler through its species record (`Data.pokemon[shown].name`) -- following a Transform's presented species, then the form the mon is wearing, then its own species -- and only then falls back to `mon.name`. The record names are normalised once at load to the base species' name by g9-gui 3.0.4 (`ui/display_names.lua`), so an alternate form reads "PONYTA" instead of "PONYTA-GALAR"; the scene reads whatever the record says, so it is correct with or without that mod. The scene also PRE-WARMS BOTH leads' sprite sheets (through g9-battle-sprites) the moment the battle screen is created -- not only when the pokeball starts its flight -- so a sheet has the whole intro, not just the ball's 0.45s, to bake before the mon materialises.

PATCH 4.0.3: Pokemon now learn moves DURING a scene battle, and the battle pauses on the game's own learn screen until the question is answered. A level-up granted by the exp award that comes with a move now either learns it at once (a free slot, announced) or -- full moveset -- parks the turn and pushes `src.ui.MoveLearnMenu` (the same screen the bag/party pickers use), so the player answers with the real TryingToLearn / forget-list / AbandonLearning flow; the next turn cannot start until the move is learned or declined. Gen 2's engine already emitted a textless `choose-forget` record the scene ignored (the fifth move was silently dropped); the scene now handles it, and Gen 1's scene arm re-issues the native per-level move checks (so Gen 1 now also announces level-ups it previously omitted).

PATCH 4.0.4: g9-Battle-Scene once again LOADS at all. LÖVE's LuaJIT caps a function at 200 active locals and `battle_screen.lua`'s factory had crept one over the line, so the Mod Manager reported `function at line 186 has more than 200 local variables`, marked the mod [failed], and every layout battle silently fell back to the native screen. The factory's 58 top-level helper closures were folded into ONE table (`FN`), which drops it back to 145 active locals without changing a byte of behaviour. Separately, a wild SPECIAL BOSS (bossKind tera / dynamax / gigantamax / mega) now PLAYS ITS TRANSFORMATION when it appears: it fades in as its ordinary self and the same clip a mid-battle transformation uses runs over it, the declared look (crystal film, size ladder, form) landing on the clip's reveal beat. Costume only -- nothing is activated (battle_forms owns WHEN a gimmick fires and a wild mon never reaches its enemy-trainer path).

PATCH 4.0.5: the bundled example background `cave.png` is removed from `assets/backgrounds/` (the folder now ships only its `README.md` again). A gym / Elite Four / Champion fight whose own numbered backdrop is missing now walks an EXPLICIT fallback chain instead of borrowing the map's terrain: its own tag (`gym1`..`gym16` / `elitefour1`..`elitefour4` / `champion`) -> `gym.png` (a new generic gym tag) -> `grass.png`. An indoor gym therefore no longer falls through to the cave ground, and one dropped-in `gym.png` covers every gym / league fight. The chain is FINAL -- with neither fallback present the fight draws nothing -- and every other tag keeps the old single map-terrain fallback. `background.lua`'s `FALLBACK` table drives it; the bare `gym` tag was added to the vocabulary so `gym.png` is discovered.

PATCH 4.0.6: the BACKGROUND row is now the scene's master on/off. `background.lua` exports `M.sceneWanted()` (`M.option() ~= "off"`), which g9-battle-sample reads before routing a fight: AUTO (the default) or a pinned tag keeps the custom scene; OFF sends every fight to the game's own battle screen -- ground art and layouts alike. The scene's own drawing is unchanged (asked to draw with no art it still degrades to the white field); this is purely the routing answer a caller consults. Pairs with g9-battle-sample 1.2.5, whose renamed "2v2/3v3/4v1" row now only picks the layout (OFF = force the singles scene).

PATCH 4.0.7: two visual-comfort changes. (1) The MEGA, DYNAMAX/GIGANTAMAX and TERA transformation clips no longer flash-bang the viewer: each clip's full-screen white is capped at `FLASH_ALPHA` (0.30) -- a 30%-opaque white instead of the old solid 1.0 -- and the whole flash curve (the coloured wash in, the white window, the fade) scales with it, so the beat is dimmer throughout, never just at its peak. The reveal beat still sits inside that window, and the sprite is still held as a black silhouette (Dynamax) or a white one (mega/Tera) across it, so the form swap stays hidden. This is a FIXED value; there is no option for it. (2) A new WHITE HP BAR option (OFF by default) draws a Pokemon's HP bar as a translucent WHITE band (white at 40% opacity) instead of the game's green / yellow / red colour, so the bar is a soft white strip that lets the sprite read through rather than a bright coloured one. It applies to both sides and to both layouts -- the over-the-head stat readout and, with FANTASY COMBAT on, the party status list -- and only the HP bar changes: the exp bar, the numbers and the rest of the readout keep their colours.

PATCH 4.0.9: CRITICAL -- a switch-in now takes the hit instead of the Pokemon that switched out. When a player switches, the enemy's move for that turn used to land on the mon leaving the field: the engine captures a move's target as a real mon at QUEUE time, and because the outgoing mon did not faint the engine's own "chosen target fainted, redirect" rescue never fired. Fixing it: `battle_screen.lua`'s switch branch now repoints every already-queued action whose target is the outgoing battler onto the arriving one (both `moveQueue` and `queuedActions`), so the action follows the SLOT. This applies to the enemy's own move and to any ally-directed move aimed at the switching slot. On Gen 1 a benched mon switched in had no engine battler at all (`battlersByMon` is built from the starting field roster), so `native.lua`'s Gen 1 `state:useMove` now builds one the first time the mon is actually used (idempotent, side from `mon.multiSide`) -- without it the retargeted hit would have been dropped in silence.

PATCH 4.0.8: corrects 4.0.7's second change and re-tunes the HP bar. (1) The option is now WHITE ROW, not WHITE HP BAR: it repaints each FANTASY COMBAT party row's own BACKGROUND panel as a translucent white panel (white, 40% transparent / 60% opaque) instead of the usual dark surface, and touches nothing else -- the name, HP bar, level, exp bar and status tag inside the row keep their own colours. It has no effect unless FANTASY COMBAT is on, and the whole native over-the-head white-bar path from 4.0.7 was removed. (2) The FANTASY COMBAT party list's HP bar is no longer the old bright green / yellow / red: `fantasy_combat.lua`'s `COL.good` / `COL.warn` / `COL.bad` are now one shared depth anchored on the user's #00A36D -- good `#00A36D` (0.000, 0.639, 0.427), warn `#A38F00` (0.639, 0.561, 0.000), bad `#A30000` (0.639, 0.000, 0.000) -- with the yellow and red darkened to that same saturation and value. This colour is always used and is not tied to the WHITE ROW option. The transformation-flash cap from 4.0.7 is unchanged.

PATCH 4.1.0: PIVOT TIMING -- a self-switch move's switch-in now takes exactly the hits that were still pending when the user left, and the turn ORDER decides which those are. Teleport (-6 priority, it acts LAST) therefore takes the opponent's hit first and switches in a mon exposed only to entry hazards and field conditions; U-turn / Volt Switch / Flip Turn acting EARLY switch first, and the opponent's not-yet-delivered move then follows the slot and lands on the switch-in. g9-battle-engine already captures each action's target as a real mon at queue time, but its self-switch primitive ended the whole round early, so a pivot switch-in took nothing. Now the engine's `combat/switch_primitives.lua` tags its self-switches with `battle.__g9PendingSelfSwitch`, `combat/turn_order.lua`'s `resolveTurnActions` stops on that at the switch (no end-of-turn), emits a `pivot-switch` event, and the new `mod.exports.resumeAfterPivot(battle, incoming, outgoing)` re-enters on the SAME round -- repointing every not-yet-acted actor aimed at the mon that left onto the one the scene sent in -- then runs the end-of-turn normally. `battle_screen.lua` advertises `battle.__g9SceneHandlesPivotSwitch`, opens its mandatory bench pick (`beginPivotSwitch` / `openPivotSwitch` / `choosePivotMon` / `refusePivotCancel` / `applyPivotSwitch`) and resumes through `Combat.resumeAfterPivot`; `native.lua`'s Gen 2 arm exposes the same resume. A scene that does not advertise the flag keeps the old behaviour exactly (the round ends at the switch), so the two mods stay independently installable.

PATCH 4.2.0: the ENEMY's over-the-head stat readout now reads like the FANTASY COMBAT party list. (1) A new ENEMY STAT WHITE option (ON by default) sets the enemy readout on a rounded, translucent panel -- white at 80% transparency (20% solid) -- so its name, level and HP bar stay readable over a busy field; OFF matches that panel to the party rows' usual dark surface (`fantasy_combat.lua`'s `COL.panel`) instead, and the readout's own text (name, level readout and gender glyph) turns WHITE so it stays readable on that dark surface. (2) In BOTH states the enemy's HP bar now takes the party list's own muted colour family -- the same `COL.good` / `COL.warn` / `COL.bad` (#00A36D / #A38F00 / #A30000) and the same >0.5 / >0.2 thresholds the ally rows use -- instead of the native bright green / yellow / red. `battle_screen.lua`'s `FN.drawGuiBox` gained a 12th `enemyStat` argument: only the enemy call site passes it, so the player's readout and the ally party list are byte-identical to before. On the tile path the native bar is drawn first (still keyed, so the mon reads through the empty part of the bar) and its FILL is repainted in the muted colour over exactly the cart's own channel; on the no-tiles fallback the muted `hpBar` table is handed to `drawHpFill` instead. The player's readout is untouched.

PATCH 4.3.0: in-battle move learning now runs on g9-gui's modern learner when that suite is installed, and on a plain WHITE field when it is not. `Screen:beginMoveLearn` asks g9-gui for the screen id it registered (its new `mod.exports.moveLearnScreenId`, read through `mod.find`, lazily and fail-open) and pushes THAT; the engine's screen registry resolves a mod's record before its own builtin, so a boot with g9-gui gets its opaque 540x360 `ui/move_learn.lua` page and the battle behind it is left exactly as it was. With g9-gui absent, failed or its MODERN UI switched off, the scene pushes the engine's own `src.ui.MoveLearnMenu` and marks the pause `owned = false`, and `Screen:drawContent` paints the whole 320x180 design field plain white before anything else -- no Pokemon, no HUD, no terrain -- for as long as the learn question is open (the scene is the drawn base under the pushed classic menu, so the sheet covers the screen). The white field lasts exactly the pause: the flag lives on `self.learn`, which `beginMoveLearn` sets and the learner's own `onDone` clears. A mod-owned screen (any registry-provided factory, not just g9-gui's) suppresses the sheet, so this never blanks a page out from under another suite's learner.

PATCH 4.4.0: which learner answers the in-battle learn question is now the SCENE's own decision, not a bare "is g9-gui installed?" probe. A new MODERN MOVE LEARN row (ON by default) joins BACKGROUND as the routing pair: the modern learner runs only while the custom scene is ON (BACKGROUND not OFF) AND MODERN MOVE LEARN is ON; a boot with EITHER row OFF gets the game's own classic `src.ui.MoveLearnMenu` -- its "is trying to learn ... Delete an older move?" question, the four-move forget list, the HM guard and the whole native "1, 2 and... Poof!" sequence -- drawn over a plain WHITE field with no Pokemon, HUD or ground art behind it. `Screen:beginMoveLearn` now builds the learner through one new `FN.pushLearner`, which resolves g9-gui's published id through `src.ui.Screens` and pushes that page ONLY when its factory is a registry record (`__modOwned`) that actually builds; every other case -- either row OFF, no suite, no published id, or a modern screen whose constructor throws -- requires `src.ui.MoveLearnMenu` BY NAME and pushes that directly, so a registry record can never shadow the classic learner and a modern screen that fails to build can never leave the native question over a live battlefield. `owned` is the push's own answer, so the white sheet (FN.drawLearnSheet) is guaranteed whenever the classic learner is what actually went up.

PATCH 4.4.1: MULTI-HIT HP ANIMATION -- the HP bar now drops ONCE PER LANDED HIT of a multi-hit move instead of collapsing every hit into a single drop. The engine applies every hit before the scene narrates any of them (Gen 1's `state:useMove` runs the whole move and fills its native queue; Gen 2's `resolveTurnActions` resolves the turn in one call), and the display is a chase: `Screen:armHpAnim` points it at the HP vector each event carries and `Screen:stepHpAnim` walks the bars to it, so a hit animates only if its OWN event carries its own HP. On Gen 2 each landed hit already emits its own `damage` event with the defender's HP as of that hit (confirmed against the real `gen2/Battle.lua`'s `hitOnce`/`dealDamage`), so the bar already stepped per hit. On Gen 1 it did not: `native.lua`'s `drainNativeMove` forwarded only the native queue rows that had `.text`, so every `say` the scene saw already carried the FINAL total and a two-hit move animated as ONE drop. `drainNativeMove` now walks that queue in order and emits a textless beat for every `{ drain = true, stopAt = <hp after this hit> }` row, stepping a pre-move HP vector forward (latched by `state:useMove` and copied per beat by `state.copyHpSnap`). Double Kick's bar therefore settles at hit 1's HP and then hit 2's -- and a recoil drain on the user lands after the target's, exactly as the native queue orders them. The beats are ordinary `damage` events, so the damage numbers and the rest of the narration are unchanged. `Screen:installEventProbe` also publishes the screen on the battle (`battle.g9Scene`) so the Gen 1 model can reach `Screen:snapshotHp`.

PATCH 4.4.2: the ENEMY STAT WHITE panel is now 60% SOLID, and the DARK variant's white text is real white. (1) The white panel's fill was 20% solid (80% transparent) and read as barely there over a busy field; `FN.enemyPanelColors` now returns `{ 1, 1, 1, 0.60 }`, so the enemy's name, level and HP bar sit on a solid-enough surface while the sprite still reads through the remaining 40%. The dark variant and the ally party rows are unchanged. (2) With the option OFF the readout's text was invisible: the cart's font pages are BLACK glyphs on transparent (Font.drawBox's own header says so), so `love.graphics.setColor(1,1,1)` could NOT lighten them -- black tinted any colour is still black -- and the white ink the 4.2.0 patch intended had never actually appeared. The fix is a one-line fragment shader, `FN.WHITE_INK_SHADER` / `FN.whiteInkShader()`, that emits `vec4(1.0, 1.0, 1.0, Texel(tex, tc).a)` -- WHITE with the glyph's own alpha -- so the tile glyphs are RECOLOURED rather than tinted. `FN.drawGuiBox` binds it ONLY around the enemy name / `<LV>` tile / level digits / gender glyph draws while `enemyStat` is set and the panel is the dark variant, and restores the previous shader immediately after (before the native HP badge and bar cells, which set their own palettes). The shader is created once, `pcall`-guarded and cached; a build without shader support falls back to the plain draw exactly as before, and the ON state (black ink on the white panel) and the player's readout are untouched.

PATCH 4.4.3: Dynamax and Gigantamax are now told apart by the scene, and a Dynamaxed mon's readout SHOWS its HP multiplier -- as a DRAW-ONLY skin, never a write. (1) KIND DETECTION: `Ev.dyn.kindOf(screen, mon)` answers "gigantamax" or "dynamax" from the declared boss kind (`battle.g9BossKind.kind`), then a live `mon.form` (what battle_forms stamps for a G-Max, authoritative once the change has landed), then the engine's `isGigantamaxEligibleSpecies`, else "dynamax". Both announcements are kind-aware -- the pre-reveal line ("X is Dynamaxing!" / "X is Gigantamaxing!") and the reveal ("X Dynamaxed!" / "X Gigantamaxed!") -- so a plain Dynamax no longer borrows the Gigantamax wording (user-reported; the pre-reveal line had said "Gigantamaxing!" for every Dynamax). (2) THE HP SKIN: battle_forms deliberately never writes max/current HP (its `src/hpscale.lua` applies the `(30 + L)/20` bonus as reduced incoming damage, and paints its own readout through `battle.overlay` -- a hook the vanilla screen fires and this scene, which replaces that screen, does not), so a Dynamaxed mon's real numbers never moved here and the scene had nothing to show for the multiplier. The scene now keeps a screen-keyed, draw-only record (`Screen:startDynamaxHpSkin` / `clearDynamaxHpSkin` / `dynamaxHpSkinFor` / `dynamaxHpSkinDisplay` / `updateDynamaxHpSkin`), and `FN.drawGuiBox` gained a 13th `hpSkin` argument that scales the readout's shown HP and max AS IT DRAWS. Nothing assigns to `mon.hp` / `mon.maxHp` / `mon.stats.hp`, and the record lives on the SCREEN (keyed to the mon's table), so no save data is touched. The curve is the user's spec, in seconds from the sequence's start: over the first second the MAX climbs x1 -> x(30+L)/20 while the current stays x1, so the bar's fill dips (a bigger pool, the same HP); over the next second the CURRENT climbs to match, so the fill returns to its old ratio; after 2.0s both hold at the multiplier. (3) SNAPBACK: the skin is dropped the moment the mon stops being Dynamaxed/Gigantamaxed -- faint, switch-out, battle end and the 3-turn expiry all clear it -- and a Dynamax that arrives with no staged clip (an enemy trainer's, a thin install) is picked up on the next tick. The readout then returns to the real values. (4) DAMAGE: because the damage battle_forms lets through is dmg/M and the skin multiplies the numbers back up by M, the floating damage label would have understated the hit, so `Screen:armHpAnim` scales its delta by M too -- the player reads the RAW hit, exactly as specified. The FANTASY COMBAT party rows take the same skin. All 72 new harness assertions pass, plus the existing scene regressions.

PATCH 4.4.4: the GIGANTAMAX FACTOR is now the gate battle_forms was missing. battle_forms decides Gigantamax purely from the mon's SPECIES (its `src/dynamax.lua` `activate()` reads `deps.gigantamax[mon.species]` and its `arm()` reads `deps.gmaxMoves(battle.data, mon)`), so on its own it Gigantamaxes EVERY eligible species whatever the engine's own per-mon `gigantamaxFactor` says -- the Factor was inert. `Screen:applyGimmickActivation`'s focused region (the existing `FN.focusBattlePlayer` wrap, which already runs the arm and the `battle.turn_started` emit against the FORM's owner) is now also wrapped by `FN.withFormsSpecies`, which reads the engine's exported `getGigantamaxFactor` / `isGigantamaxEligibleSpecies` (with bare-field fallbacks for a build without g9-battle-engine). A mon WITHOUT the Factor is temporarily handed a stand-in species (`FN.FORMS_FALLBACK_SPECIES`, `"RATTATA"` -- a real species, present in the data and absent from battle_forms' gigantamax map) so it Dynamaxes plainly with ordinary Max Moves; a mon WITH the Factor keeps its real species, so an eligible one Gigantamaxes exactly as before. The swap uses the same pcall-and-restore discipline `focusBattlePlayer` already applies to `battle.player`, so a raising battle_forms call can never leave a saved Pokemon's species renamed, and it is skipped entirely for a species that is not Gigantamax-capable (nothing to gate). `Ev.dyn.kindOf` now requires the Factor as well as eligibility, so a Factor-less eligible mon is ANNOUNCED as Dynamaxing -- matching what will actually happen.

PATCH 4.4.5: the in-battle move learner no longer faults to the game's classic screen on a platform whose option rows come back in a different SHAPE. The scene already routes the learner off its own two rows (BACKGROUND not OFF and MODERN MOVE LEARN ON), but `FN.modernMoveLearn` compared the stored value to the exact string `on`, so a boot (or a save) that reports a choice row as a boolean, a number or a differently-cased string read as OFF and pushed the engine's classic learner over the white field -- the Android report: MODERN MOVE LEARN ON + BACKGROUND AUTO still fell to native. Both rows are now read through ONE `FN.optionOnOff` normaliser: `on` / `true` / `yes` / `1`, the boolean `true`, and any non-zero number are ON; `off` / `false` / `no` / `0`, the boolean `false` and an empty string are OFF; and an unreadable value answers nil so the caller fails OPEN to the row's own default (ON), exactly as before. `FN.pushLearner` also (1) refreshes the screen registry (`Screens.invalidate`) and re-resolves ONCE when the first lookup yields a non-mod-owned factory, so a builtin cached before g9-gui registered its record (a load-order race that can differ by platform) can never shadow the modern learner for the rest of the session, and (2) logs a single warning naming the id it asked for when the modern row is ON but no mod-owned screen could be resolved -- the one line that explains a platform whose registry or g9-gui differs, instead of a silent native fallback.

PATCH 4.4.6: the mod no longer declares an `optional_dependencies` edge that pointed at its own DEPENDENCY. `manifest.json` listed both `g9-battle-sprites` under `optional_dependencies` and `g9-battle-engine` under `dependencies`; `g9-battle-sprites` in turn lists this scene (`g9-Battle-Scene`) under its own `optional_dependencies`, so the two edges form a 2-cycle. The loader treats an `optional_dependencies` entry as a real ORDERING edge (it is folded into the same topological sort as a hard dependency, see `src/mods/Loader.lua`'s `_mergeOrder`), so a cycle cannot be ordered -- the loader breaks it by dropping the higher-id edge and logs `optional dependency loop broken at g9-Battle-Scene` -- and, worse, the edge it kept put the lower-priority mod FIRST, so this scene (priority 100) was being loaded before `g9-battle-engine` (its HARD dependency), which the engine tolerates only by deferring the engine's own wiring. Nothing here needs the sprites to be loaded first: every sprite lookup goes through a lazily-resolved module handle at battle time (and `resolveSprite` fails open when the mod is absent), so the edge was purely declaratory and the correct fix is to remove it. `optional_dependencies` is now `[]` and the loader orders the engine before the scene again, with no cycle warning. (The same shape -- the lower-priority half's optional edge being the spurious one -- was removed from `battle_forms` -> `g9-battle-engine` and `g9-battle-engine` -> `g9-gui` in the same pass; all three were reported as `optional dependency loop broken at ...` on the same boot.)

PATCH 4.5.0: a new 4v4 preset (`layouts/4v4.lua`, `fourVFour = true`) with an exclusive adjacency ruleset, gated on that one flag so no other layout can be reached by it. Rule 1: in a 4v4 EVERY teammate and EVERY foe counts as adjacent to the caster -- the same "all allies = all allies" a boss fight reports, extended symmetrically -- so a single-target move (and the target picker) offers the whole field; a nil moveId roster query stays full. Rules 2 and 3: an OFFENSIVE SPREAD move (`all-opponents` like Rock Slide / Muddy Water / Surf, or `all-other-pokemon` like Earthquake, resolved through the engine's own isSpreadMove with the move-def `target` as fallback) is the one carve-out -- it keeps NORMAL positional adjacency on the ENEMY side, so it reaches at most three of the four enemies and never all four; an `all-other-pokemon` move still receives the whole ally list and so damages every ally while keeping the same three-enemy cap. Distance-capable moves and the boss/horde exceptions are unchanged, and no damage formula or spread-mitigation modifier is touched -- spread reduction still rides on the resolved target count, so it still only drops out when a single target was affected. `Screen:isFourVFourFight`/`Screen:reachAllSlots` widen the picker on the same flag. Layouts are chosen by the caller (`pushLayoutBattle("4v4", ...)`); `g9-battle-sample`'s router is unchanged.

PATCH 4.5.1: the target picker can aim at adjacent allies, and a double-battle Imposter transforms into the foe directly opposite its slot. The picker's ally machinery has existed since round 26 -- Screen:isAllyTargetable, Screen:reachableAllies and the allies-first candidate list -- but its authority, g9-battle-engine's own isAllyTargetable, only recognised the inherently ally-directed archetypes plus the selected-pokemon HEAL records, so Transform and every other status/support selected-pokemon move (Thunder Wave, Toxic, Trick, Skill Swap, Instruct, ...) fell through and the picker listed foes only. The engine now admits every non-damaging selected-pokemon move (national_dex damageClass == "status") and exports a new isAllyOnlyMove for the moves whose only legal recipient is an ally (Helping Hand, Aromatic Mist, Acupressure, Heal Pulse, Floral Healing). The scene follows: a new Screen:isAllyOnly reads that export, Screen:isAllyTargetable's stale-engine fallback also accepts damageClass == "status" / power == 0, and the A-branch candidate build now offers ONLY reachable allies for an ally-only move (empty in singles, so the move is used and fails rather than being applied to the lone enemy), allies FIRST then foes for an ally-targetable move, and foes alone for everything else. For Imposter, the scene answers the engine's new g9.request_opposite hook from its own index-aligned playerBattlers/enemyBattlers grid -- the opponent in the caster's own column, or nil when that slot is empty or its occupant is fainted -- so the ability never falls back to a different foe or to the caster's ally. And because the scene builds its own battle model (native.lua's buildBattle) without ever calling the engine's newWild/newTrainer constructors, the engine's switch-in abilities were never run for a scene battle at all: Screen:finishIntro now runs runSwitchInAbilities for every active battler once the intro ends, which is what makes a double-battle Imposter fire -- and, with the position seam, fire at the right mon.

PATCH 4.5.2: translated Pokemon names render their symbols instead of tofu. A name a game-translation mod produces -- or the engine's own modern names, which PokeAPI spells with the female/male sign (Nidoran♀ / Nidoran♂) and the star item names carry (★) -- uses U+2640, U+2642 and U+2605, which Saira does not have. A new four-glyph supplement, `assets/fonts/g9-symbols.ttf` (built from Noto Sans Symbols / Noto Sans Symbols 2), is attached to every face this mod bakes as a LOVE 11.3 `Font:setFallbacks` fallback (`fantasy_combat.lua`'s F.fonts), so the battle HUD, a party row and a move name render the glyph rather than a tofu box. No other change; the fallback only ever ADDS glyphs, and an engine without `setFontFallbacks` simply keeps the old behaviour. The same supplement, with the same wiring, ships in g9-gui (its translation layer's catalog) and g9-evolutions.

PATCH 4.5.3: the supplement is REBUILT so the scene can render every language g9-gui's translation layer now supports. Japanese and Korean catalogs were added, whose names use kana and Hangul that neither Saira nor the old four-glyph file carried, so `assets/fonts/g9-symbols.ttf` is rebuilt from Noto Sans JP / Noto Sans KR / Noto Sans Symbols 2 with the symbols (U+2640 FEMALE SIGN, U+2642 MALE SIGN, U+2605 BLACK STAR), the kana a Japanese catalog needs and the Hangul a Korean one needs (1086 glyphs, ~306 KB). The wiring is unchanged -- it is still attached to every face this mod bakes as a LOVE 11.3 `Font:setFallbacks` fallback -- and the fallback only ever ADDS glyphs, so an English boot renders exactly as before.

PATCH 4.5.4: the scene localizes the messages it sends ITSELF, and wraps translated text properly. The ROM's text is the translation mod's job, but the scene's own strings -- the item/bag refusals (`Can't use that here yet.`, `Can't throw a ball -- 2+ foes still standing!`), the FORM/gimmick messages, the run and outcome lines (`You won the battle!`), the target/switch prompts and the gimmick picker's DYNAMAX/TERA labels -- are ours, so the mod never sees them. A new `FN.localize` resolves g9-gui's translation layer (`mod.find("g9-gui").exports.translation.line`) and every message, outcome, picker and gimmick label the scene draws passes through it; without g9-gui, with the layer's TRANSLATION row off, or with no translation mod it is a no-op and the English stands. `FN.drawWrapped` now counts CODEPOINTS rather than bytes and breaks an over-long, space-less run on UTF-8 boundaries: a Japanese/Korean message has no spaces to wrap on, so before this a translated line could only overflow the box as one unbroken run (the reported "message runs past the box"). `assets/fonts/g9-symbols.ttf` is rebuilt again (1093 glyphs, 316116 B) for the codepoints the new strings add; the wiring is unchanged.
